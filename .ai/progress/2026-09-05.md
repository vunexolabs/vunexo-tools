## Vunexo Expense Manager — Project #2 started and V1 built end to end (session 1)

User asked to start project planning for a new "Expense Manager" tool. Clarified up front (it wasn't obvious from the ask alone) that this is:
- A **new, standalone app** (`apps/expense-manager/`) — Project #2 in the monorepo, not a feature bolt-on to Vunexo Billing. "Expense tracking" had actually already been scoped and deliberately locked out of Billing's V2 (`.ai/product-v2-scope.md:39`, "drifts toward accounting") — this is that deferred decision, made for real, as its own product.
- **Independent product data boundary** — own SQLite DB, own business profile, no coupling to Billing. Independent data doesn't mean zero shared code; shared monorepo tooling/non-domain infrastructure stays reusable later if it makes sense.
- **Same stack as Billing**: Rust/Tauri/SQLx backend, React/TS/Tailwind frontend.
- **Core V1 focus**: expense logging + vendor tracking + tax-deduction tracking (not a bare log, not full accounting).

User then reviewed the Round 1 plan in detail and locked four corrections before approving:
1. GST/ITC are **recorded facts, not determined ones** — the app records tax info the user supplies; it never determines statutory tax eligibility or ITC entitlement, and doesn't give tax advice.
2. A category's tax-deductible flag is a **default classification**, not an authoritative rule — overridable per expense.
3. Explicitly excluded tax filing, tax return prep, tax advice, and automatic legal-eligibility/ITC determination from V1 scope.
4. "Independent data" reworded to **independent product data boundary; shared monorepo tooling/non-domain infra reusable where appropriate** — independent data ≠ zero shared code.

User then asked to run all rounds through to a complete, working project in one push (not stop after each round for review). Executed all 9 rounds in this session:

1. **Spec + foundation** — `.ai/product-expense-manager.md` (locked V1 spec, mirrors `product.md`'s structure, carries the four corrections above plus the receipt-attachment boundary — local-only, no OCR/extraction/cloud-upload in V1 — and the broadened historical-immutability principle: a renamed vendor/category, or a category's deductibility flag changing later, must never retroactively change what an already-recorded expense shows).
2. **User flows** — `docs/expense-manager/user-flows.md`. No draft/issued state machine for expenses (deliberately simpler than Billing's invoices — an expense is either recorded or it isn't).
3. **Database schema** — `docs/expense-manager/database-schema.md`. Four tables (`business`, `vendors`, `categories`, `expenses`). Snapshot columns (`vendor_name_snapshot`, `category_name_snapshot`, `deductible`) on `expenses` are what actually implement the historical-immutability principle. `itc_eligible` and `deductible` are separate boolean facts, not one field. Single currency only (no multi-currency table). Receipt stored as an app-managed relative path (`receipts/<uuid>.ext`), same discipline as Billing's `business.logo_path`.
4. **Application architecture** — `docs/expense-manager/application-architecture.md`. `domain`/`application`/`infrastructure` layering mirrors Billing. No `TransactionManager` port — nothing in this domain does a genuine multi-table atomic write. Explicitly called out: `CreateExpense` writes the snapshot columns, `UpdateExpense` never does (except when the user re-picks a different vendor/category, which re-snapshots the newly picked one) — flagged as "the one rule most likely to be gotten wrong."
5. **UI/UX** — `docs/expense-manager/ui-ux.md`. Six sidebar sections (Dashboard, Expenses, Vendors, Categories, Reports, Settings), flat, no nesting. Categories is a single inline-edit table (mirrors Billing's Tax Rates screen) rather than separate list/detail screens.
6. **Calculation engine** — `docs/expense-manager/calculation-engine.md`. Much lighter than Billing's (no line items, no discount allocation, no multi-tax split) — every report is a SQL `SUM(...)` grouped by category/period/deductible-flag/itc-flag/vendor. Top Vendors deliberately groups by `vendor_name_snapshot`, not the live vendor row, so a renamed vendor produces separate historically-accurate rows rather than one merged one — locked as correct behavior, not a bug to fix later.
7. **Implementation** — delegated to a background-capable general-purpose agent (ran ~32 minutes, 223 tool calls) with the six locked docs plus pointers into Billing's actual source as pattern reference. Built the full backend (44 Rust files: domain/application/infrastructure layers, one migration with the literal schema from Round 3 §11, all Tauri commands from Round 4's command surface, starter categories seeded once on first run) and full frontend (32 TS/TSX files: every screen from Round 5's inventory, `features/` module mapping, hooks, Tauri type/command bridge).
8. **Testing** — 40 backend tests (business/vendors/categories/expenses incl. snapshot-immutability cases/dashboard/reports incl. every Round 6 test vector/backup+restore incl. receipt survival/domain unit tests/filesystem). All green.
9. **Release readiness** — extended `.github/workflows/ci.yml` with `frontend-expense-manager`/`backend-expense-manager` jobs (new job names, existing Billing jobs untouched to avoid disturbing any required-status-check config). Added a separate `.github/workflows/release-expense-manager.yml` (own tag prefix `expense-v*`, own `workflow_dispatch` — won't fire on anything that already exists). Added `apps/expense-manager/README.md` (no Download section yet — nothing's been built/published). Updated root `README.md` to list both projects. **Did not commit, push, tag, or publish anything** — that's a separate, explicit action for the user to authorize.

### Deviations from the locked docs (disclosed by the implementation agent)

1. Added one extra Tauri command, `suggested_backup_file_name`, not in Round 4's enumerated list — kept to avoid dead code around `domain::backup::backup_file_name`, same thin convenience Billing already exposes.
2. Round 4 named three separate `expense_repository` methods (`list_by_category`/`list_by_vendor`/`list_by_date_range`); implemented as one `ExpenseRepository::list(filter: ExpenseFilter)` with all three axes combinable — strictly more capable, matches the single `list_expenses` command surface exactly.
3. A few infrastructure ports (`file_writer`, `backup_archive`, `database_file`, `receipt_store`) aren't named in Round 4's abbreviated ports list but were the obvious things needed to build the `backup.rs`/`export.rs` use cases the doc does require — same shape Billing already uses.
4. Category Summary / dashboard category breakdown group by **current** `category_id` (a rename doesn't fragment them); Top Vendors groups by `vendor_name_snapshot` per Round 6's explicit instruction. Read as consistent, not contradictory — Round 3 says reports *can* regroup by current category, Round 6 explicitly locks vendor-snapshot grouping.
5. Period Summary groups by calendar month — not specified in the locked docs, simplest choice absent an explicit granularity control.
