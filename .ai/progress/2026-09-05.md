3. Explicitly excluded tax filing, tax return prep, tax advice, and automatic legal-eligibility/ITC determination from V1 scope.
4. "Independent data" reworded to **independent product data boundary; shared monorepo tooling/non-domain infra reusable where appropriate** — independent data ≠ zero shared code.

## Vunexo Billing — multi-country tax (`VAT_STANDARD`) fully wired end to end (session 15)

User asked for a fresh feature audit and to fully complete multi-country tax work, explicitly saying to proceed autonomously ("i'll check at the end"). Tax work was tackled first since it was the more concrete, precisely-specified half — six locked V2 design docs already fully specify a second regime, `VAT_STANDARD` (`calculation-engine-v2.md` §1, `database-schema-v2.md` §5, `application-architecture-v2.md` §4a/§4d, `ui-ux-v2.md` §3/§8).

**What investigation found**: the regime *plumbing* was already real from session 12 — `business.tax_regime_code` (CHECK-constrained to `IN_GST`/`VAT_STANDARD`), `tax_regime_snapshot` frozen at Issue on both Invoices and Quotes (with legacy-`NULL` normalization pinned to the repository row-mapping layer, per §4b), `domain::calculation::present_vat`/`split_gst` presentation functions, and a `tax_summary` report query that already grouped by `tax_regime_snapshot` unconditionally. All of that was genuinely correct and tested. But **two real dispatch bugs made the second regime silently inert everywhere a document actually renders**, both predating the V2 regime work (leftovers from the earlier GST-only era) and both never caught because nobody had ever actually switched a business to `VAT_STANDARD` and looked at a rendered document:

1. `domain::invoice_pdf::tax_rows` (backend PDF renderer) keyed its CGST/SGST/IGST-vs-neutral-"Tax" choice off `settings.country_code != "IN"`, not the document's `tax_regime_snapshot`. This is exactly the anti-pattern `ui-ux-v2.md` §3 explicitly warns the *frontend* against ("never on `country_code`... a separate, currency-display-only setting") — turns out the backend had committed the identical mistake independently. Concretely: a `VAT_STANDARD` business with `country_code = "IN"` (plausible — a business physically in India that isn't GST-registered) would have printed a GST split it never actually computed; an `IN_GST` business with a non-`"IN"` `country_code` would have printed a generic "Tax" line instead of its real, computed GST split.
2. `InvoiceEditor.tsx`/`QuoteEditor.tsx`'s totals panels had the exact same `countryCode !== "IN"` bug, independently, on the frontend side.

**Fixes**:
- `tax_rows` now takes a resolved `TaxRegimeCode` — the invoice's own snapshot, falling back to the live business's *current* regime only for a Draft preview (mirroring the file's existing `snapshot_or_live` pattern used for every other frozen field) — and dispatches `present_vat`/`split_gst` off that. Removed the now-dead `INDIA_COUNTRY_CODE` const and its stale doc comment.
- `InvoiceEditor.tsx`/`QuoteEditor.tsx` gained an `effectiveRegime` computed the same way (`invoice.tax_regime_snapshot ?? business?.tax_regime_code ?? "IN_GST"`, via a `useBusiness()` call added to each), driving the same VAT-vs-GST-split totals row.
- Replaced the now-incorrect `outside_india_the_same_tax_total_prints_under_a_neutral_label` PDF test (it was asserting the *old, buggy* country-code-driven behavior) with three tests that actually pin the correct contract: GST prints regardless of `country_code`, VAT prints regardless of `country_code`, and a Draft preview falls back to the live business's regime.

**The other real gap**: nothing in the UI let a business actually *pick* `VAT_STANDARD` — `BusinessProfileTab.tsx`/`BusinessSetup.tsx` both hardcoded `IN_GST` with no control at all, so even with the dispatch bugs fixed, no real user could ever reach the `VAT_STANDARD` path. Added:
- A Tax Regime `<select>` (India GST / Standard VAT) to both `BusinessProfileTab` (Settings) and `BusinessSetup` (first-run), with the exact low-key confirmation copy `ui-ux-v2.md` §3 locks ("Tax regime changed. Existing issued documents won't be affected. Any Draft documents will use the new regime the next time you save them.") shown inline whenever the form's pending selection differs from the saved value.
- `hooks/useTaxRegimeFields.ts` — the locked `useTaxRegimeFields(regime)` "one switch point" (`ui-ux-v2.md` §3/§8), a small lookup returning which of `gstin`/`hsn_sac`/`is_interstate` apply to a regime (empty set for `VAT_STANDARD`). Wired into: the interstate checkbox in `InvoiceEditor`/`QuoteEditor`; the GSTIN field in `BusinessProfileTab`, `BusinessSetup`, and `CustomerForm`; the HSN/SAC field in `ProductForm`. A `VAT_STANDARD` business no longer sees India-specific fields that don't apply to it, anywhere they're editable.
- A frontend `presentVat` (`lib/tauri/types.ts`) mirroring the backend's exactly, following the same "one narrow, tested exception to the frontend-never-calculates-totals rule" reasoning already established for `splitGst`.
- Updated `InvoicingTab.tsx`'s now-stale "only India's GST... is implemented" note to describe both regimes and point at where to actually pick one.

**Test strengthening**: `reports.rs`'s `tax_summary_groups_by_regime_and_excludes_cancelled` test, despite its name, had only ever exercised a single regime (`IN_GST`) plus a cancelled-invoice exclusion — it didn't actually prove mixed-regime grouping worked. Extended it to issue one invoice under each regime (switching `business.tax_regime_code` between them via `update_business`, same mechanism a real user would use) and assert two distinct, correctly-amounted `by_regime` rows — the actual "mixed-regime edge case" `database-schema-v2.md` §7 / `user-flows-v2.md` §5 call out.

**Net result**: 136 backend tests passing (was 134 — one stale test replaced by three correct ones, one existing test substantially strengthened), `cargo fmt`/`clippy` clean. Frontend `typecheck`/`lint`/`build` all clean. A business can now genuinely run on `VAT_STANDARD` and get correct results end to end: Settings → pick regime → issue an invoice → PDF prints a single VAT line → Invoice Editor totals agree → Tax Summary report groups it correctly separately from any `IN_GST` invoices in the same range.

**Deliberately not attempted, per `calculation-engine-v2.md` §1's explicit scope boundary**: a genuine third regime, jurisdiction/nexus rules, exemptions, reverse charge, tax-inclusive pricing, or destination/origin sourcing. `VAT_STANDARD` remains exactly "flat per-line rate, tax-exclusive, single aggregate" by design — nothing above tried to widen that.

## Vunexo Billing — fresh feature audit: 4 real bugs found and fixed (session 15, continued)

Delegated to a background agent with explicit instructions to read `CURRENT.md` first (so it wouldn't re-flag already-disclosed gaps), stay out of the tax-regime code just fixed, and fix real bugs directly rather than only report them. It covered Payments, Customers/Products CRUD, Quotes edge cases, Statements/Reports, Backup/Restore/Export, and cross-cutting error handling. Verified its work myself afterward (full `cargo build && cargo test && cargo fmt --check && cargo clippy` run) before trusting the report.

**Fixed** (all backend, `src-tauri/`, no frontend files touched):
1. **`application/ports/infrastructure_error.rs`** — `InfrastructureError::from(sqlx::Error)` classified FK violations only via SQLite's `SQLITE_CONSTRAINT_FOREIGNKEY` (787) extended code. Every `ON DELETE RESTRICT` in this schema actually fails as an *immediate* constraint check, which SQLite reports as `SQLITE_CONSTRAINT_TRIGGER` (1811) instead — confirmed empirically, not just from documentation. Net effect: the entire "can't delete a customer/product that has invoice history" feature has silently fallen through to a raw, unfriendly infrastructure error instead of the intended clean `Conflict` message **since V1**, and nobody caught it because `delete_customer`/`delete_product` had zero automated tests before this session. Fixed by also checking the message text (`"FOREIGN KEY constraint failed"`), plus a regression test against a real in-memory SQLite RESTRICT constraint.
2. **`sqlite_customer_repository.rs`/`sqlite_product_repository.rs`** — `has_invoices` (drives the archive-vs-delete UI decision) only checked `invoices`/`invoice_line_items`. Since V2 (session 12) added `quotes.customer_id`/`quote_line_items.product_id` as RESTRICT references too, a customer/product referenced only by a Quote (never invoiced) showed a Delete button the database would then refuse. Widened the `EXISTS` check to cover both tables; `Conflict` messages in `customers.rs`/`products.rs` updated to say "invoice or quote history."
3. **`sqlite_report_repository.rs`** — `tax_summary`'s `by_regime` grouping grouped on the raw `tax_regime_snapshot` column. A legacy pre-V2 invoice has that column `NULL`; a post-V2 `IN_GST` invoice has it explicitly `'IN_GST'`. Both are the same effective regime but were reported as two separate rows instead of merging. Fixed with `COALESCE(tax_regime_snapshot, 'IN_GST')`, grouping by the full expression rather than its alias (SQLite resolves a `GROUP BY` name against a real column of the same name first — the agent's first attempt at aliasing silently didn't work, caught and fixed before reporting).
4. **`application/products.rs`** — `update_product` was missing the "unit is required" validation `create_product` already had, so an edit could clear a product's unit to blank. Added the matching check.

141 backend tests passing (was 136 after the tax work; +5 from this audit), `fmt`/`clippy` clean.

**Looked at and deliberately left alone** (each with a stated reason, not silently skipped):
- `TaxSummaryTab.tsx`'s comment calling multi-regime grouping "dormant" is now stale since session 15 made `VAT_STANDARD` real — cosmetic, in a file adjacent to tax-regime code that was explicitly off-limits this pass.
- `hooks/useTheme.tsx`'s `react-refresh/only-export-components` warning — same harmless class as the already-disclosed `useCurrency.tsx` one; recommend adding it to `CURRENT.md`'s disclosed-warnings list rather than "fixing" it.
