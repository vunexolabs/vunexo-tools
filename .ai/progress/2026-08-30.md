# Session 2 — PDF generation

Picked up the "Next up" list's item 1. Everything from the earlier sessions was already committed as `6209e06` before this started (`CURRENT.md`'s "uncommitted work-in-progress" warning was stale — corrected there now).

## Library choice: `printpdf` 0.12, `default-features = false` + `text_layout`

Composes the invoice operator by operator (`Op::ShowText`/`DrawRectangle`/`DrawLine`/`UseXobject`), which is what "real layout control, not print the webview" needs. Dropping default features drops the `html` feature and the whole azul-layout/fontconfig HTML-to-PDF stack with it.

`text_layout` had to be added back for one specific reason, found the hard way: **font subsetting only exists on that feature.** `prepare_fonts_for_serialization` has a `#[cfg(not(feature = "text_layout"))]` arm that always embeds the full font. Without it a one-page invoice came out at **743 KB**; with it, **32 KB**. Same document, same code otherwise. Worth the dependency.

Note the API differs between the two configurations — `ParsedFont` is a stub struct without `text_layout` and a newtype over azul's with it (`face.font_metrics.units_per_em`, `get_glyph_width_internal`, not `face.units_per_em`/`get_glyph_width`). `src/infrastructure/pdf/fonts.rs` targets the `text_layout` shape.

Also raised the crate's `rust-version` 1.77 → 1.88 (printpdf 0.12 requires it; local toolchain is 1.98).

## Embedded font: DejaVu Sans 2.37, Regular + Bold

`src-tauri/assets/fonts/` (+ `LICENSE.txt` — Bitstream Vera, permissive). The PDF base-14 fonts carry no `₹`, `₦`, `₫`, `₺`… and the app prints in 55 currencies, so an embedded face was unavoidable. DejaVu covers every symbol in `lib/currency.ts` **except** Bengali `৳` (BDT) and `﷼` (SAR) — verified with fontTools against the actual table, not assumed.

Those two are handled rather than ignored: `Fonts::can_render` checks glyph coverage at render time and the renderer prints `BDT 2,360.00` instead of an amount with a silently-dropped symbol. Same fallback covers a currency code the table doesn't know at all.

Subsetting means the 1.4 MB of source faces cost a few KB per output file.

## Layering

Kept to `architecture.md` rule 3 — `printpdf` never leaves `infrastructure/pdf/`:

- `domain/currency.rs` — Rust mirror of `lib/currency.ts`'s `CURRENCIES` (symbol + ISO 4217 decimals), plus grouped formatting. **Keep the two lists in sync.** Indian lakh/crore grouping for INR/PKR/LKR/NPR/BDT, uniform thousands elsewhere; the frontend's own formatter has no grouping, which is fine on screen but not in print.
- `domain/invoice_pdf.rs` — `InvoicePdfDocument`: every string the PDF shows, already formatted. Snapshot-vs-live resolution, the CGST/SGST/IGST decision, date/quantity/basis-point formatting, the totals rows all live here, testable without producing a byte of PDF. **This is `split_gst`'s first real server-side caller** — it and `GstSplit` are no longer dead code.
- `application/ports/invoice_pdf_renderer.rs` + `application/pdf.rs` — the port and the orchestration (load invoice/settings/business/customer/payments, build the document, call the renderer).
- `infrastructure/pdf/{fonts,canvas,invoice_renderer}.rs` — measurement, placement, pagination. It formats nothing.

One deliberate seam: money amounts cross into the renderer as **numbers only**, no symbol. Whether an amount can print as `₹1,234.00` or has to degrade to `INR 1,234.00` depends on the embedded font's glyphs, which only the renderer knows.

`canvas.rs` works in **millimetres from the top-left**; the flip to PDF's points-from-bottom-left is confined to one function.

# Session 3 — Backup, restore, and export (Settings → Data)

"Next up" item 2. The spec turned out to be wider than `user-flows.md` §9's backup/restore: `ui-ux.md` §6 also locks three CSV exports and a distinct JSON "everything" export, with an `export_data(entity, format)` command. Built the whole Data tab.

## `.vbx` is an archive, not a database copy

Per `database-schema.md` §9: `metadata.json` + `database.sqlite` + `assets/`. Implemented with the `zip` crate (`default-features = false`, `deflate` only — the other backends pull C toolchains to compress what is already a compact SQLite page store).

Two things in here are load-bearing:

- **The snapshot is `VACUUM INTO`, never a file copy.** The live database runs in WAL mode; copying the main file captures a database missing every committed change still sitting in the WAL, and can catch a torn page mid-write. `VACUUM INTO` takes its own read transaction and emits one self-contained file with no sidecars.
- **Archive members are untrusted input.** `safe_file_name` reduces every `assets/` member to a single ordinary file name, so a member called `../../.ssh/id_rsa` is skipped rather than written outside the data directory. Tested directly.

## Restore ordering

The risky operation in the whole app, so the order is deliberate and commented at the call site:

1. **Validate first** — never close the pool for an archive we would reject anyway.
2. **Extract to a staging file beside the live database** — a corrupt or truncated archive is discovered while the real database is still intact and serving.
3. **Only then** close the pool, delete the `-wal`/`-shm` sidecars (they belong to the *old* database and SQLite would try to replay them over the restored file), and `rename` the staging file into place. Same directory, so it's a move rather than a copy that could half-complete.

Then the command calls `app.restart()` and never returns. That isn't a convenience: every repository still holds the pool `restore_from` closed, so continuing to run would mean serving a database nothing can read.

The integration test proves it's a real rollback rather than a no-op — it backs up, *changes* the data, restores, then reopens the file fresh (which is what the app itself does after restarting) and asserts the pre-backup value is back.

## Errors the user can act on

Picking the wrong file in the restore dialog was initially surfacing as `Infrastructure`, which `ui-ux.md` §3's error mapping renders as the generic "something went wrong, your data is safe" — useless when the actual problem is "that's a holiday photo, not a backup". Both rejection reasons now come back as `Validation` with a specific sentence:

- a newer `format_version` → "this backup was made by a newer version … update the app, then restore it" (the version exists so old archives can be *migrated*, so the check is `>`, not `!=` — an older backup is accepted);
- anything unreadable → "this file isn't a usable Vunexo Billing backup: it may not be a .vbx backup, or it may be damaged". The underlying zip/IO message is dropped rather than forwarded, since it carries paths and internals.

Found this because clippy flagged `BackupRejection::Malformed` as never constructed — the warning was pointing at a real hole, not noise.

## Exports

`domain/export.rs` is pure and holds the part that's easy to get quietly wrong: **RFC 4180 CSV escaping**. A customer called `Smith, Jones & Co`, or an address with a newline in it, silently shifts every later column if you "join with commas". Fields are quoted when they contain a comma/quote/CR/LF, embedded quotes are doubled, records end CRLF. Tested against exactly those cases, including that a multi-line address stays one field.

**Money exports as a plain decimal with no grouping and no symbol** (`1234.50`) — deliberately unlike the PDF. An export is read by a spreadsheet or an importer, and `₹12,34,567.89` is data loss dressed as presentation. Currency travels in its own column. Currency-correct decimal counts still apply (JPY 0, KWD 3).

Other decisions worth keeping:

- **Exports include archived records.** An export is a copy of what the business has, not of what the pickers currently offer. Tested.
- Products CSV resolves `tax_rate_id` to the rate's name and percentage — an export full of foreign keys is useless in a spreadsheet.
- Invoices CSV is one row per invoice with the reconciliation figures (subtotal/discount/tax/total/paid/balance), not line items. The JSON export is the lossless one.
- JSON covers every table in `database-schema.md` §13 as **domain shapes**, per §6's "not a blind SQLite table dump". It walks invoices one at a time to attach line items and payments — N+1 on a local SQLite file for a one-shot export, which is the right trade against adding repository methods that nothing else needs.

# Session 4 — Make `business.logo_path` app-managed

Item 3 from "Next up": closing the gap flagged during the backup slice — `logo_path` stored wherever the user's file happened to be, while `database-schema.md` §9 assumes assets live under the app data directory. Backup archived the file and restore wrote it to `<data_dir>/assets/`, but the restored `logo_path` still pointed at the *original* absolute location, so restoring onto a different machine (or a different user account, since the data directory's real path embeds the username) left the logo unresolved even though the archive had a perfectly good copy of it.

## The fix

`domain/business.rs` gets a small, pure vocabulary:

- `managed_logo_path(extension)` → `"assets/business-logo.png"` — always **relative**, deliberately, since the data directory's absolute path contains the OS username and won't be the same on a different machine or account.
- `is_managed_logo_path`/`resolve_logo_path` — the whole legacy story in two functions. An absolute value is untouched (that's a *pre-managed* logo, and it still works on the machine that chose it); a relative one resolves against wherever the data directory currently is.

`BusinessUseCases::import_logo_if_chosen` runs on every create/update: if the incoming `logo_path` is absolute, it's copied into `<data_dir>/assets/business-logo.<ext>` via a new `FileWriter::copy`, and the field is rewritten to the relative form before the row is saved. Idempotent by construction — a path that's already relative (already managed) passes straight through, so re-saving the form without touching the logo never re-copies it.

Both consumers of a stored `logo_path` — `PdfUseCases::render_invoice_pdf` and `probe_business_logo` — now resolve through `resolve_logo_path` before touching the filesystem, at the one seam in each that knows where the data directory is. `domain::invoice_pdf` and `infrastructure::pdf` stay unaware any of this exists, same as before.

**One-line migration, free of charge:** the picker always hands back an absolute path, so "absolute" is exactly "not imported yet" for *any* business row, new or years old. The very next time the existing legacy logo (an absolute `~/Documents/...png`) gets saved through the form — even untouched — it gets imported and rewritten automatically. No migration script, no manual step.

## Frontend

`BusinessProfileForm`'s local `fields` state was never re-synced after a save — a real, if minor, bug found while wiring this up: after `onSave` returns the business with its now-rewritten `logo_path`, the form kept showing the stale absolute value it had sent, and saving again (even unrelated fields) would silently re-import the same file. Fixed by setting `fields` from what the save actually returned.

## Verification

# Session 9 — First CI run, and the real bug it caught

User confirmed the line-discount UI and Dashboard Overdue click-through both work in the running app (session 7's changes). Asked what's next; pushed the 4 local commits from sessions 5–8 to `origin/main` (`gh auth status` confirmed the active account is `vunexolabs`, matching the repo, per this agent's own `reference_github_auth` memory) — first time this repo's CI has ever run.

## It failed — two things, one real

`gh run view --log-failed` after the run finished:

1. **CI infra bug, not a code bug**: the `frontend` job pinned `node-version: 20`, but `pnpm@11.7.0` (the version pinned in `packageManager`) requires Node ≥22.13 and crashed outright (`ERR_UNKNOWN_BUILTIN_MODULE: node:sqlite`, from pnpm trying to use a Node 22+ builtin on Node 20). Fixed by bumping to `node-version: 22`.

2. **A real cross-OS bug in `domain::business`**, caught only on the `windows-latest` leg of the backend matrix (`ubuntu-latest`/`macos-latest` both passed): `is_managed_logo_path`/`resolve_logo_path` used `Path::is_absolute()` to tell a legacy absolute logo path from an app-managed relative one. That function means "absolute *for the OS this binary is compiled for*" — `Path::new("/Users/someone/Documents/logo.png").is_absolute()` is `false` on Windows (Windows absolute paths need a drive letter or UNC prefix), so a Unix-style legacy path was misjudged as *managed* there. Two tests failed as a direct result: `a_legacy_absolute_path_still_opens_on_the_machine_that_chose_it` (asserted directly) and `a_freshly_chosen_absolute_logo_is_copied_and_the_path_rewritten` (the same misjudgment meant `import_logo_if_chosen` skipped importing the logo at all).

This isn't just a test artifact — session 4's whole `business.logo_path` app-managed work exists so a `.vbx` backup survives being **restored onto a different machine**, and "different machine" can mean a different OS. The bug is symmetric: a Windows-origin backup's legacy `C:\...` logo path restored onto a Mac/Linux box would have hit the mirror-image failure (`Path::is_absolute()` on Unix is `false` for a `C:\...` string too), silently `data_directory.join()`-ing a Windows path fragment instead of opening it as-is.

## Fix

Replaced both functions' `Path::is_absolute()` calls with a new pure-string `looks_absolute()` (`domain/business.rs`): true if the string starts with `/` (Unix), starts with `\\` (UNC), or matches a drive-letter prefix (`[A-Za-z]:`). Deterministic regardless of which OS compiled the code or which OS produced the original path. Added `a_legacy_path_is_recognised_as_absolute_regardless_of_which_os_wrote_it`, parametrized over Unix/Windows-drive-backslash/Windows-drive-forward-slash/UNC forms, so this can't silently regress the way `Path::is_absolute()` did. The two originally-failing tests needed no changes — they pass once the function they call is fixed.

## Verification

116 tests (was 114), `cargo fmt`/`clippy` unchanged (still the one known warning). Re-pushed both fixes (the Node version bump and the `looks_absolute` fix) together; the CI run this triggered is what the top of `CURRENT.md` reports.

## Why this matters beyond the one bug

This is exactly what session 8 flagged as open — "nobody has built/run the app on a real Windows or Linux machine" — paying off within one push. A macOS-only development loop cannot catch platform-specific standard-library behavior differences like this one; CI running on all three target OSes is what surfaces them before a user does.

## The real bug this surfaced: unsigned macOS builds are "damaged", not just "untrusted"

User downloaded the actual `.dmg` from the published release to test on their own Mac — macOS refused to open it at all: **"is damaged and can't be opened, move to trash."** Not a corrupt download. This is a known Gatekeeper behavior specific to **completely unsigned Apple Silicon (arm64) binaries**: macOS requires every arm64 executable to carry *some* code signature, even an untrusted ad-hoc one; with zero signature at all, Gatekeeper reports "damaged" instead of the milder "unidentified developer, open anyway?" prompt an ad-hoc-signed or signed-but-unnotarized app would get. The README's macOS guidance ("right-click → Open") was itself wrong for this specific error — that workaround only applies to the milder prompt, and doesn't even appear as an option when Gatekeeper says "damaged."

Two fixes:

1. **Immediate, for the build already downloaded**: `xattr -cr "/Applications/Vunexo Billing.app"` strips the quarantine attribute Gatekeeper can't verify. Documented as a fallback in the README.
2. **Root cause, for every future build**: added `"macOS": { "signingIdentity": "-" }` to `tauri.conf.json`'s `bundle` section (confirmed the exact key casing — `macOS`, not `macos` — against `@tauri-apps/cli`'s bundled `config.schema.json` rather than guessing). `"-"` tells `codesign` to ad-hoc sign — no Apple Developer certificate or CI secret needed. This should turn future macOS builds' Gatekeeper experience into the ordinary "unidentified developer" prompt (where right-click → Open works) instead of the hard-blocking "damaged" error. **Not yet verified against a fresh build** — the next release run is what proves this, not just the config existing.

Notable decisions made in this round:
- **Quote state machine**: `DRAFT → ISSUED → ACCEPTED → CONVERTED`, with `DECLINED`/`EXPIRED` (derived, like V1's `OVERDUE` badge) and `CANCELLED` as terminal side-branches. `ACCEPTED` is a real stored state (a business needs to know "yes, not yet billed" as distinct information). A Quote is editable in `DRAFT` only — V2 does *not* extend V1's "edit an issued document" allowance to Quotes, since a Quote has no payment history to protect (cancel-and-duplicate instead, same as a cancelled invoice). Conversion is exactly-once and terminal — a Quote cannot produce two invoices; a business wanting to bill the same accepted work twice duplicates the resulting *invoice* instead.
- **Quotes get their own numbering series** (`QUO-` vs `INV-`), independent sequence, same never-reused/immutable-once-issued rules as V1 invoice numbering. A converted Quote keeps its own number permanently for traceability; the resulting Invoice gets a normal freshly-generated number at its own issue time.
