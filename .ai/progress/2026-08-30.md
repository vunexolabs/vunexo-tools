## Payments

Full payment lifecycle: `record_payment`/`update_payment`/`delete_payment`/`list_payments_for_invoice`, domain → port → SQLite repo → use case → Tauri command, wired into `main.rs`. Status auto-recalculates in the same transaction as the payment write (Issued → PartiallyPaid → Paid based on `amount_paid` vs `total`). Overpayment is recorded in full and flagged, never clamped. `CANCELLED` invoices reject *new* payments but existing payments on one can still be edited/deleted (record-keeping correction) — recalculation correctly keeps `CANCELLED` terminal rather than reviving it.

Frontend: `PaymentPanel` (history + inline edit/delete + "record new" defaulting to remaining balance), wired into both the Invoice Editor and a quick "Record Payment" row action on the Invoices List.

6 integration tests: partial→full transitions, overpayment recorded exactly, edit-down recalculates, delete-only-payment reverts to Issued, record-against-cancelled rejected, edit-on-cancelled keeps it Cancelled.

## UX audit ("make it solid, no flaws")

User asked to systematically check existing features against the locked spec. Found and fixed:

- **No confirmation dialogs anywhere** — `ui-ux.md §3/§7` names a "confirmation dialog" as a required shared component; it didn't exist. Built `components/ConfirmDialog.tsx`, wired into: cancel invoice (with optional reason, per spec), delete draft invoice, delete customer/product (not spec-named but an obvious one-click-irreversible-delete flaw).
- **Missing "Overdue" filter** on Invoices List — explicitly named in `ui-ux.md §5`, wasn't in the filter bar. Client-side filter over the already-backend-computed `is_overdue` flag (no new backend query needed).
- **Line-item tax rate wasn't wired to real tax rates** — the reported bug ("I added a tax rate but it's not reflected"). Root cause: the Tax % field was a bare text input, picking a product never populated it. Fixed: dropdown of real tax rates + "Custom %" override; picking a product now uses its assigned rate or the Settings default.
- **Totals didn't update until Issue** — fixed with a 600ms-debounced autosave on every line/discount edit, calling the same real `update_draft_invoice`/`edit_issued_invoice` the Save button uses. Still zero client-side money math — it's an automatic save, not a calculation.
- **No quick-add for customer/product from the invoice editor** — `ui-ux.md §3` already specified a "searchable picker with a persistent + Create new row," just never built. Built `components/SearchablePicker.tsx` (generic combobox) + `components/Modal.tsx`, used for both customer and per-line product selection, with inline create via the existing `CustomerForm`/`ProductForm`.

## EditIssuedInvoice

Backend: `EditIssuedInvoiceData` domain type, `InvoiceRepository::update_issued`, `InvoiceUseCases::edit_issued_invoice`. The one part that needed care: confirmed against `user-flows.md`'s exact wording that editing an issued invoice **re-snapshots customer/business from current live data at the moment of the edit** — deliberately different from a bare `UpdateCustomer` call, which must never touch old invoices. Never touches `payments` or `status`, even when the new total drops below what's already paid (stays whatever status it was, UI shows it as overpaid via `PaymentPanel`, which already had that math).

3 integration tests: re-snapshot reflects current data (proven by changing the live customer's address *between* issue and edit, asserting the edit picks it up but a bare `UpdateCustomer` on a different invoice wouldn't), status/payments untouched on overpayment, Draft/Cancelled invoices reject the edit.

Frontend: Issued/PartiallyPaid/Paid are now fully editable (previously read-only except payments) — "Save Changes" button, autosave routes to the right endpoint based on status. Added Duplicate and Cancel (with the same `ConfirmDialog`) directly to the editor footer, since it was already being touched — previously only reachable from the list.

## Currency / country support

Scoped explicitly with the user first: dynamic *display* (symbol, decimal places) based on Settings' `currency_code`/`country_code` (which already existed but were unused); **not** a rebuild of tax-regime logic — GST stays India-only, noted as a future-version item (see `CURRENT.md`'s Known gaps).

- `lib/currency.ts` — 60 countries → currency mapping, correct ISO 4217 decimals (JPY/KRW=0, BHD/KWD/OMR/JOD/TND=3, rest=2) and symbols.
- `hooks/useCurrency.tsx` — one `CurrencyProvider` mounted at the app root (`main.tsx`), `useCurrency()` hook exposing `symbol`/`formatMinor`/`parseToMinor`. This is a deliberate, narrow exception to "no global client-state store" — cross-cutting read-mostly config, not feature data.
- Replaced every hardcoded `₹`/`formatMinorAsRupees`/`parseRupeesToMinor` across 7 files (InvoicesList, ProductForm, ProductsList, PaymentPanel, Dashboard, InvoiceEditor, types.ts) with the currency-aware equivalents. Renamed the underlying functions to `formatMinorAsAmount`/`parseAmountToMinor(input, decimals)`.
- Settings → Invoicing: Country/Currency are now real dropdowns (picking a country auto-suggests its currency, still independently overridable); saving calls `refresh()` on the currency context so the change applies app-wide without a restart.

One subtlety handled: `toEditableLine`/`toEditableLines`/`mergeEditableLines` in `InvoiceEditor.tsx` are module-level functions (can't call hooks), so `formatMinor` is threaded through as a parameter from the component instead. `useCurrency()`'s `formatMinor`/`parseToMinor` are `useCallback`-memoized on `decimals` so effects that use them can list them as a dependency without either a stale-closure bug or a re-run-on-every-render loop.
